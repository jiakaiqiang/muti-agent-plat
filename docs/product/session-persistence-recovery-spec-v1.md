# 群聊持久化与恢复 Spec v1

## 目标与证据

2026-09-14 实际会话在 17:39:50 因 `PERSISTENCE_REVISION_CONFLICT` 于 brief_generation 失败，17:42:38 点击继续转入 EXECUTING，随后因缺少任务契约进入 WAIT_USER_DECISION。日志同时存在停止回执持久化冲突。逐笔冲突来源尚无日志证据；不能归因于用户点击停止。

修复运行时事务一致性、失败恢复入口和停止提示，保留消息、产物、设备身份、目录绑定和权限。不自动重跑用户会话、不调整模型/供应商、不把 Harness 产品化。

## 验收条件

- AC1：运行时逻辑操作、调用日志和 Context 更新不使用全库 revision 作为提交条件；事件/outbox/设备更新不能制造无关冲突。
- AC2：相关集合在同一数据库事务读取最新值并提交；普通集合写入、事件追加和 outbox 更新遵守相同锁规则。第一版允许同集合串行，不承诺同集合不同行并行。
- AC3：异步提交和缓存刷新不覆盖等待期间的本地新修改；普通快照写入不把其他事务新增的记录删掉或覆盖未修改字段。
- AC4：数据库失败不启动模型；仅明确可重试的事务错误有限重试，回调只允许纯数据变更。重复 reservation/receipt 不增加模型次数、不放开未知停止屏障。
- AC5：失败卡片、通用 resume 与文本重试按真实失败阶段恢复；契约缺失不能转入执行。重复确认不重复启动；旧确认不能批准当前另一项决策。
- AC6：仅用户停止/超时停止等存在待确认停止的调用产生停止确认通知；正常完成回执可以落库和 ack，但不显示“可以继续会话”。重复回执不重复通知。
- AC7：保留维护/迁移的严格全局 CAS；file 模式事务失败保持旧状态。
- AC8：真实隔离 PostgreSQL 并发、失败回滚、缓存覆盖、停止屏障、契约失败恢复及双端既有 API 回归通过。

## 影响与边界

主要影响 server persistence、context-management、runtimes、local-runtime、sessions。Web/桌面沿用 API 和各自样式。无 schema 迁移，无清库，无目录授权变更。已有错误会话需在修复验收后由用户明确继续；不能用测试覆盖实际业务数据库。

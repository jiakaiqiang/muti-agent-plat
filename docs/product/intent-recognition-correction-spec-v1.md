# 意图识别、路由与纠错 Spec v1

草稿生成恢复语义（2026-10-20，IRC-R12）：已通过校验的无执行效果草稿计划生成失败后，用户可显式申请新的有限预算生成操作。必须保留旧调用/失败/预算历史、绑定原计划与当前需求版本，重传只重放收据；已保存可发布结果不得重新生成，未知停止或失效计划不得重试，暂停不隐式恢复。连接故障保护仍有效，受理不等于生成成功。

> 日期：2026-10-19。状态：实施中；部分切片已验证，完整业务验收尚未通过，当前范围见 Checklist。
> SDD 四件套：[Spec](intent-recognition-correction-spec-v1.md) → [Plan](../design/intent-recognition-correction-plan-v1.md) → [Task](../implementation/intent-recognition-correction-task-v1.md) → [Checklist](../quality/intent-recognition-correction-checklist-v1.md)。

## 1. 目标与依据

失败恢复语义补充（2026-10-20，IRC-R05/IRC-R12）：用户显式重试尚未取得有效语义的原消息时，可以创建新的有限预算识别操作，但必须保留原输入和旧操作全部失败/预算历史。网络重传、重载恢复、格式修复和快照重建不构成新的用户请求，不重置预算。同键重放返回原回执；未知停止不能开始新操作，连接故障等待期不能被重试绕过，202 不表示已完成识别。新操作仍受相同权限、版本与最终效果校验，不隐式恢复业务。

本专项采用规格驱动开发（Specification-Driven Development，SDD）：先固定用户可观察行为和验收条件，再选择实现方案、拆任务、补失败回归和实现，最后依据实际证据验收。本文定义“必须做到什么”，不把模型输出合法或 HTTP 成功直接等同业务正确。

输入为已形成的三份文档：

- [系统开发设计](../design/intent-recognition-correction-system-development-design-v1.md)：技术合同、模块、状态、事务和迁移依据。
- [14 个开发任务](../implementation/intent-recognition-correction-development-v1.md)：IR00–IR13 的原始实施分组。
- [58 个验收场景](../quality/intent-recognition-correction-acceptance-v1.md)：IA01–IA24、IC01–IC18、IF01–IF16 的完整输入、前提和预期。

历史问题来自 [2026-10-19 评测报告](../quality/intent-evaluation-2026-10-19/README.md)。已有 339 项相关回归通过，新编诊断 52/70、真实 Codex 旧/新路径分别 18/20 和 19/20、HTTP 纠错 4/7；这些不同口径不能合并为线上准确率。真实模型测试没有执行专业业务，原连接 401，PostgreSQL 场景未验证。

四件套初版只生成开发文档；此后用户已授权按文档实施，具体进度和证据记录在 Task/Checklist。文档存在不表示系统已修复。四件套组织执行，不取消原三份文档：Spec 固定行为，Plan 引用详细技术方案，Task 细化原 IR 分组，Checklist 是实际验收状态与证据入口。发现矛盾时先修订对应规格/设计并保留变更理由，不在代码中静默选择另一种行为。

## 2. 范围、非目标与交付模式

范围：首轮/后续消息识别、确定性命令、需求关系、上下文继承、效果与授权、澄清、版本纠错、约束替换、重试、持久化/恢复、Web/Desktop 和质量灰度。

沿用 NestJS 单进程模块、Context Pipeline v2、WorkItem、Decision Ledger、Tool Authority、LogicalOperation、租约、Outbox 和现有 Runtime。非目标：新微服务、第二套上下文管线、模型训练、Harness 产品模块、重写专业 Agent、切换生产连接。

两种多意图交付模式须明确区分：

| 模式 | 必须提供 | 不能宣称 |
| --- | --- | --- |
| clarify（首期默认） | 完整识别多个目标、展示顺序/未决项，未明确前阻止业务派发 | 自动执行有序多任务计划已完成 |
| ordered_plan（后续独立启用） | 逐段依赖、幂等、失败恢复、跨纠错版本效果复用 | 以新版本幂等键为由重做已完成步骤 |

正式部署比例、性能/费用限额需在目标环境测量后固定。本规格不虚构线上 SLA；这不阻塞本地合同、安全规则和隔离测试开发。

## 3. 用户场景

| 场景 | 用户需要的行为 |
| --- | --- |
| 只读分析 | “解释报错，不要改代码”只分析；生成建议不等于实施建议 |
| 评测并保存报告 | 能在隔离环境运行测试、保存指定报告，业务源码保持不变 |
| 补充当前需求 | “不是新任务”“另外补充”不会仅因关键词创建新任务 |
| 恢复或控制 | “继续”依据真实状态处理；“不要暂停”不能被解析为暂停 |
| 模型故障 | 消息保留并告知系统阻塞；不会用错误规则代替模型发起业务执行 |
| 澄清选择冲突 | 两端选择相反答案时明确反馈冲突，不能都显示成功 |
| 理解有误 | 可以纠正原理解，及时冻结明确目标的后续派发，看到何时真正生效 |
| 旧约束替换 | 30 分钟替换 10 分钟后，后续上下文和执行使用 30 分钟 |
| 多目标消息 | 每个目标、顺序和实际进度可见，第二个目标不藏在自由文本指令中 |

## 4. 功能要求

以下每个 IRC-R 编号都在第 6 节对应同号 IRC-AC；Plan 和 Task 不得降低其约束。

| 需求 ID | 必须满足的行为 |
| --- | --- |
| IRC-R01 | 首轮、后续、结构化选择和纠错进入统一管线。先持久化和裁决，再允许启动 Brief/专业派发；问答不强制创建 WorkItem。 |
| IRC-R02 | 语义输出包含分段目标、对话行为、需求关系、目标、效果、禁止项、原文证据、缺失项和依赖。模型仅提交提案，服务端形成有限动作计划。 |
| IRC-R03 | 回答/读取、产物写入、源码修改、测试、命令和外部写入分别授权；否定有对象与范围。既有授权可在有效范围内复用，子任务不得扩权，Runtime 不能约束时阻断。 |
| IRC-R04 | 区分补充、相关新需求和独立新需求；相关任务仅继承显式有效集合，独立任务不继承旧任务专属决定。否定新任务不能反向触发创建。 |
| IRC-R05 | 精确命令先于模型处理，统一状态守卫；执行中“继续”不重复派发、完成后“继续”澄清、明确 pause/cancel 不受模型故障阻塞。 |
| IRC-R06 | 服务端独立校验关系/动作/上下文、引用、状态、风险和授权。modelConfidence/validationScore 不代表正确概率，任何分数不得抵消硬错误。 |
| IRC-R07 | 暂停/完成等状态允许受限的无工具消息识别；不能因此开放业务执行。停止未确认、删除、epoch 不匹配仍阻断新模型进程，消息及明确纠错可先保存。 |
| IRC-R08 | 澄清绑定 Session、routing、confirmation、版本、选择及 actor；同选择幂等，相反选择 409，不存在/过期/跨范围卡片不得被接受。确认关系不等于授予执行权限。 |
| IRC-R09 | 已有理解通过独立纠错流程追加版本。明确目标的纠错接收即持久化派发屏障；定位不明先澄清。区分接收、停止中、待对账和已生效，不覆盖历史。 |
| IRC-R10 | 纠正决定必须定位旧决定及 revision；新决定与旧 supersede 在同一事务提交。缺目标澄清；子任务只局部覆盖继承约束，不静默废弃父任务决定。 |
| IRC-R11 | 派发、Adapter 启动和结果发布检查执行版本；过期结果只入审计，不写回/触发旧下一步。已完成外部效果走对账/补偿，不能伪称已撤销。 |
| IRC-R12 | 故障按类型处理：瞬时有限重试、认证配置错误不重复同连接、结构修复带具体错误、语义歧义澄清、效果未知先对账；所有识别重试共享持久化预算。 |
| IRC-R13 | 消息、计划、确认收据、纠错屏障、账本、投影和 Outbox 按事务边界提交；并发/重启不丢屏障、不重复效果，File/PostgreSQL 语义等价。 |
| IRC-R14 | 多意图有完整分段，禁止截断后执行或自由文本附加动作；clarify 默认保守。有序执行启用时依赖无环，重试和纠错不重做已完成效果。 |
| IRC-R15 | Web/Desktop 显示识别、澄清、系统阻塞、选择冲突及纠错生效状态；双端操作、刷新、SSE 乱序不导致错误提示成功或状态倒退。 |
| IRC-R16 | 每次识别可追踪代码、合同、策略、profile/model、快照、输出、权限、版本、attempt 和效果；未报告的 tokens/cost/transport 重试次数标未知，日志不泄露凭据。 |
| IRC-R17 | 独立标注评测按状态/入口/模型分层，预先允许合理拒绝与缺前提澄清；检查实际业务效果，不以模型分数或 HTTP 202 替代正确性和纠错成功。 |
| IRC-R18 | 历史记录可读、迁移 additive；旧未知授权不得从 requiresCodeChanges 猜测补齐。旧客户端适配须可唯一绑定，新合同禁止无能力 worker 接管。 |
| IRC-R19 | 先修复当前主路径再 shadow/灰度；shadow 不产生业务效果；回滚版本必须理解新记录和屏障并保留硬校验，不能回到不安全兜底。 |
| IRC-R20 | 快照有界且标记遗漏，原文和目标引用服务端核验；附件/历史/模型文字不能自行授予新权限，@、reply、Session、dataEpoch 和授权范围不可越界。 |

## 5. 关键行为示例（Given / When / Then）

### B01：只评测与保存报告

- Given：用户绑定隔离测试项目，未授权修改业务源码。
- When：“评测当前系统并保存 Markdown 报告，不要修改业务源码。”
- Then：计划区分 run_tests/write_artifact/source prohibition；报告存在，源码 hash 不变，测试临时写入受限；无能力约束的 Runtime 返回 blocked。
- 对应：IRC-R01/R03；IA03、IA24、IF14。

### B02：澄清选择竞态

- Given：同一个未解决确认卡，两个客户端持有同一有效 revision。
- When：分别提交 continue_current 和 independent_new，可使用不同幂等键。
- Then：一个结果被原子采纳，另一个明确 409；只创建预期任务/收据，不将原结果当作纠正成功。相同选择重发返回同结果。
- 对应：IRC-R08/R13；IC01–IC04。

### B03：纠正旧约束

- Given：登录任务有 confirmed 的 10 分钟约束及明确 revision。
- When：“改成 30 分钟，原 10 分钟作废。”
- Then：冻结受影响派发，核对运行效果，新版本提交时原子 supersede；新上下文/Brief/执行只使用 30 分钟。缺少旧目标则澄清，不捏造 ID。
- 对应：IRC-R09/R10/R11；IC09–IC16。

### B04：401 与格式错误

- Given：一次识别操作尚有有限预算。
- When：连接返回 401。
- Then：同连接一次后系统 blocked，原消息保留，无关键词执行兜底。
- When：另一独立操作首次输出缺少字段。
- Then：允许一次带具体错误的修复；两种情况都不能重置原 operation 的预算。
- 对应：IRC-R12；IF01–IF05。

### B05：多目标与状态

- Given：登录任务停在真实 Brief 确认卡。
- When：“先继续当前登录任务，再创建独立天气任务。”
- Then：保留两段；“继续”不自动批准 Brief；首期澄清阻止业务派发，天气目标不继承登录约束。
- 对应：IRC-R04/R05/R14；IA14、IF10–IF13。

## 7. 质量门与限制

独立封存集至少 500 条，两人独立标注并仲裁，以会话划分开发集/封存集，同版本至少重复 3 次。候选发布目标：动作/关系点估计 ≥95%、关键类别召回 ≥95%；同时报告样本量、置信区间、macro-F1、澄清/拒绝情况和实际效果。重复运行不能算独立自然样本，点估计不能当作正确性保证。

安全与一致性用例在启用范围内必须全过；不能通过删除失败题、放宽授权或把未知记零获得通过。IF10/IF11 在 ordered_plan 未启用时标“能力未启用”，并验证配置不能绕过；其余必需能力缺验证不得标通过。

迁移、灰度和正式发布仍按项目授权规则执行。缺独立数据库、目标 Runtime 或真实客户端证据时，Checklist 记阻塞/未验证及影响范围。历史诊断、纯模型判定和模拟成功不替代这些证据。

## 8. 规格变更与完成定义

每次行为变化先定位 IRC-R/IRC-AC，说明为何变化，再同步 Plan 决策、Task、Checklist 的期望和版本。保留旧评测原输出与分数，不能事后改 gold 掩盖失败。

实现完成需要：启用范围所有 AC 有真实证据，迁移/恢复和双客户端通过，质量与回滚门满足；部分阶段交付只声明已覆盖范围。当前四份文档均为待实施规格，没有产品通过项。

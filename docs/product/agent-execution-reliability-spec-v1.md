# Spec：Agent 执行可靠性与调用效率修复

[设计 Plan](../design/agent-execution-reliability-plan-v1.md) · [实施 Tasks](../implementation/agent-execution-reliability-tasks-v1.md) · [验收 Checklist](../quality/agent-execution-reliability-checklist-v1.md)

## 1. 目标与交付状态

让需求确认、架构、开发、验证、返工、交付连续推进；故障时有限等待、明确说明原因、保留有效进度，并从必要的失败步骤恢复。

用户已授权按四件套开发。2026-09-14 已实现业务指纹、有界调用预算、停止回执、接单预检、讨论限制、版本化提交与候选恢复，并完成隔离验证。实际证据与限制见 Checklist；真实模型效果未采样，原运行服务未重启。Harness 是交付规程，不作为新增业务功能。

## 2. 诊断基线

来源为本会话上一轮在 2026-09-14 对本地 8099 后端的只读检查，以及 HEAD `6cdbefb91ca863d4985b495d38d0aa784b57695f` 上的未提交代码。此表是历史观测，不是本次重新采样或新版本效果。

样本会话：`b0fe9fec-501d-401e-9e92-3801d67d285e`，需求为贪吃蛇增加排名和音效。复核入口：`GET /api/sessions/:id/debug/runtime-invocations`、`GET /api/sessions/:id/debug/intent-routing`、`GET /api/sessions/:id/events`。

| 证据 | 观测 | 含义 |
| --- | --- | --- |
| B01 | 需求讨论 325 秒；架构讨论 836 秒后 ENOTFOUND；前端讨论 2073 秒后 HTTP 502，重试 561 秒成功 | 上游故障和串行讨论共同增加等待 |
| B02 | brief_generation 1168 秒；StructuredOutput 首次数组字段错误，约 458 秒后纠正成功 | 业务执行与格式提交耦合 |
| B03 | 架构接单 931 秒；执行 600 秒超时；再接单 61 秒，再执行 600 秒超时 | 控制调用重、重试重复接单 |
| B04 | 同一后续消息已发生 6 次 system-intent-router 调用，累计上报 101586 token；快照反复产生 SNAPSHOT_STALE | 事件计数失效与重建标记覆盖形成重复识别 |
| B05 | 今日调用 contextEnvelope 约 3–8 KB，但多次累计用量明显更大；模型名多为 claude_code，缺少完整 streamMetrics | 不能仅以初始 Prompt 大小推断实际成本，也不能精确拆分上游排队和推理时间 |

生成需求契约前约 83 分钟，用户确认后的第一次架构节点尝试约 36 分钟；用户确认等待另计。历史错误还包括 424/503/524、Schema 不兼容，横跨不同代码版本，不构成当前版本失败率。

修复前的关键实现依据（以下不是当前实现状态）：

- `ContextManagementService.isSnapshotCurrent` 比较全部事件数量。
- `SessionsService.processIntentRouting` 用 reasonCodes 中的 SNAPSHOT_REBUILT 限制重建；`SemanticIntentRouterService.finish` 覆盖 reasonCodes。
- `OrchestratorService.runDiscussion` 顺序等待参与者；`runOneTask` 超时重试重新进入接单。
- `RuntimeInvocationService.invoke` 的系统调用入口与 Orchestrator 的监督逻辑分离。
- Local Runtime 每次建立隔离目录；本地 Claude 参数尚未消费 resume。

## 3. 范围与不变量

范围：消息路由、调用监督、故障分类、接单预检、讨论上下文、输出提交、检查点恢复、诊断指标和双端状态展示。

不变量：

- 保留用户选择的已发布工作流快照，不自动删减架构、开发或质量节点。
- `accepted` 仅表示能够执行，不代表产物通过验收；沿用现有接单拒绝、执行阻塞、质量 revise/reject 的不同语义。
- 质量自动返工取决于实际节点合同，不能因 Agent 名字含“质量”就修改节点类型。普通 agent 节点继续使用既有阻塞恢复分支。
- 保留 Context v2 唯一主链路、授权目录隔离、按工作区 FIFO 写回、冲突检查和原产物 Diff。
- Web 与桌面保留独立布局，共享状态合同和必要的小组件。
- 不新增用户认证、模型供应商、后台通知渠道；不自动开放本地文件给新的远端模型。
- 本轮不提交、部署、重启真实服务、改真实任务或生成安装包。

## 4. 功能规格

### REL-001：路由快照只依赖相关业务变化

新增专用于路由有效性检查的业务版本/指纹。新需求、工作项切换、相关决策、任务范围、待确认目标和影响动作合法性的状态变化必须使旧判断失效；心跳、工具日志、用量统计等非决策事件不得使其失效。不能简单删除所有版本校验。

### REL-002：识别重建与应用有界且幂等

持久化独立 snapshotRebuildCount，最多自动重建一次，任何 reasonCodes 更新不重置它。同一 sourceEventId/routingId 在租约和业务版本校验下至多应用一次。超过重建或操作预算进入明确等待，不递归或定时无限调用。明确且唯一目标的控制命令走规则，模糊目标保持澄清。

### REL-003：共享操作预算

系统路由和编排共用操作监督协议。逻辑操作预算覆盖排队、准备、Provider 调用、退避、格式纠正和补上下文；子调用不重置父截止。受限控制模型操作初始总上限 120 秒、最多 2 个平台调用，含快照重建和失败重试。规则命令模型调用数为零。

长任务采用有限的节点/操作上限和有效进展超时，使用明确策略版本；实施时从当前有效配置迁入，不直接把未经采样的阈值当作优化结果。120 秒是初始配置与故障收敛门槛，不保证语义结果在此时间内成功。

### REL-004：有效进展与停止确认

分别记录传输连通、有效模型/工具活动、实际业务产物。心跳、重复状态和重复错误不延长有效进展时限；长工具通过工具作用域进度与截止监督，不靠单条 tool_started 无限续期。取消传播至具体进程/请求，未确认停止时禁止替代执行，迟到结果不得改变业务终态。

### REL-005：故障分类与连接级隔离

区分网络/DNS、认证、限流、临时上游失败、协议和 Schema 不兼容、工具失败、业务阻塞。只重试可恢复错误，尊重 Retry-After 和父预算。按 connectionId/modelId/协议隔离故障；禁止以 runtimeType 单独作为隔离键。替代运行仅使用原授权和允许列表内的可用候选。

### REL-006：明确任务程序预检

已指定执行人的任务先校验职责配置、Runtime、权限、目录、前置产物和工具能力。充分满足条件时以规则预检通过进入执行；不足或有歧义时保留 blocked/rejected 或轻量模型判断。记录 decisionSource，不伪造 Agent 说过“接受”。质量验收不得被预检替代。

### REL-007：接单和上下文可复用

预检/接单结果绑定任务范围、Agent、目录版本、权限、工具和上游产物版本；执行重试不无条件重新接单。任何影响有效性的条件变化必须重检。用户改派和明确拒绝不能被旧缓存覆盖。

### REL-008：讨论和节点上下文收窄

需求讨论只解决影响确认的缺失信息与冲突；架构节点聚焦本次变更。上游结果按引用与有限摘要传递。仅无依赖且只读的咨询允许受限并发，合并顺序确定；当前无模型容量证据时默认并发 1。必要意见缺失不得静默跳过确认条件。

### REL-009：执行产物与提交结果分离

系统采集真实文件差异、命令退出码和验证证据；模型提交最小必要结论、产物引用和阻塞说明。保持严格合同，不静默补造业务字段。格式修复不能重跑开发、重新执行有副作用的工具或写回。有效候选产物按检查点保留；无可靠候选时不能声称可恢复。

### REL-010：节点内恢复

记录准备、候选产物捕获、验证、提交和写回的状态及版本。格式错误恢复提交，测试失败恢复修复/复测，下游失败保留上游成功结果。候选目录和文件引用需受控、可校验；CLI 原生续接仅在安全且受支持时使用，否则以候选产物和摘要重建上下文。

### REL-011：持久化与合同兼容

操作计数、预算、检查点和输出合同版本持久化；服务恢复不自动重放未确认副作用。新增简化输出合同使用显式版本选择，存量运行仍可验证原输出合同，不引入旧版 Context 执行路径。缺失检查点的旧任务显示不可恢复边界，不补造记录。

### REL-012：两端展示真实执行阶段

群聊区分准备、等待上游、模型执行、工具执行、校验、重试、停止待确认、等待用户。前端以服务端状态为准；模型名称未知明确记为未知，不能以 claude_code 冒充具体模型。保留停止、继续、草稿、阅读位置和跨端同步。

### REL-013：可观测与分层验收

记录逻辑操作与物理调用关联、具体模型（可确认时）、策略版本、各阶段耗时、错误、重试原因、累计用量及数据缺失标记。缓存 token、缺失用量和计费分开，缺失不能记为实际零成本。分别报告隔离故障验证、完整流程验证和真实模型样本结果。

## 5. 效果与边界

| 问题 | 修复后可验证的行为 | 不能据此承诺 |
| --- | --- | --- |
| 同一消息重复识别 | 心跳新增不重建；重建/调用次数有界；动作只应用一次 | 所有自然语言无歧义 |
| 接单成本高 | 明确任务无完整 CLI 接单调用；重试复用有效预检 | 所有 Agent 都能执行任务 |
| 故障层层重试 | 共享截止，不重复放大；停止未确认不重启 | 上游永远可用 |
| 格式失败重做工作 | 已捕获产物保留，仅修复提交 | 无检查点也能恢复进程内全部思考 |
| 返工重复上游 | 复用有效结果，依赖变化可追溯失效 | 任意质量节点都自动返工 |

不预先承诺固定端到端分钟数或生产成功率。目标是先消除确定性无效调用，再在相同任务、模型、目录和工作流下比较时延与完成率，人工等待单列。

## 7. 未决项与默认处理

真实模型/连接选择、采样费用、生产时限属于部署验收输入，采用已有允许配置，本轮未切换真实连接或付费采样。咨询并发默认 1；简化提交仅对声明 v2 能力的本地工程 Runtime 启用。自动无副作用提交修复限支持 safe-mode 的 Claude CLI，禁工具与自定义参数；Codex 保留候选，但不自动执行未经证明无副作用的提交修复。没有有效检查点时明确说明并使用既有节点重试。

服务端工程子进程在重启后缺少可信结束回执时保持停止未知，不因用户点击继续就自动解除。新本地 CLI 的结束回执支持持久化、断线重传和服务端确认；旧 CLI 的未知执行仍需完成停止核对。该限制不能通过扩大超时或清空操作记录绕过。

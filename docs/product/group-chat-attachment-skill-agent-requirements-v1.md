# 群聊附件、Skill 插件注册与 Agent 协同需求 v1

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档名称 | 群聊附件、Skill 插件注册与 Agent 协同需求 |
| 版本 | v1 |
| 状态 | 需求已确认，可进入设计与实现 |
| 适用产品 | Agent Cluster 群聊协作工作台 |
| 目标用户 | 发起群聊协作任务的人类用户 |
| 参与对象 | 主 Agent、群聊 Agent、系统管理员、群聊管理员 |

## 2. 背景

当前群聊工作台已经具备多 Agent 协作基础，但用户仍缺少统一的附件上下文入口，以及明确、可发现、可管理的 Skill 调用方式。用户需要能够在同一条消息中上传图片或文件、选择一个能力 Skill，并指定一个或多个候选 Agent；系统再根据语义把能力分配给最匹配的 Agent，展示协同过程，并由主 Agent 汇总结果。

本需求将以下能力统一到群聊输入和协作链路中：

1. 图片和文件上传、预览、识别、引用和生命周期管理。
2. 通过 `/` 选择 Skill，并由插件注册中心管理 Skill。
3. 通过 `@` 选择一个或多个候选 Agent，并支持自动语义路由。
4. 结构化保存 `/Skill`、`@Agent` 和附件引用，保证历史消息可追溯、可恢复。
5. 通过协同任务面板展示 Agent 分发、阶段性输出、失败、重试和重新汇总。

## 3. 产品目标

### 3.1 目标

- 让用户能在输入框内直接上传最多 4 张图片和 4 个文件。
- 让图片在上传后立即获得可供 Agent 使用的内容理解结果。
- 让文件以安全、可追溯的文件引用方式进入 Agent 上下文，避免无条件注入完整文件文本。
- 通过 `/` 以分类列表选择一个 Skill 能力。
- 通过 `@` 选择负责执行需求的 Agent，支持多候选 Agent 的语义路由。
- 没有 `@` 时，由主 Agent 负责理解、分发和汇总。
- 让用户能够看到完整的 Agent 协同过程，并在失败时单独重试、重新汇总。
- 让 Skill 具备系统级、群聊级、个人级的分层管理能力。

### 3.2 首期非目标

- 首期不把 Agent 注册到插件注册中心；Agent 由独立的 Agent 管理模块维护。
- 首期插件注册中心只支持 Skill，未来可扩展其他插件类型。
- 首期图片识别不做 OCR，只做图片内容理解和描述。
- 首期不支持 ZIP/RAR 等压缩包。
- 首期不设计 Agent 主动上传附件。
- 首期不设计 Agent 的主动移除能力。
- 首期不提供附件单独删除；只能删除包含附件的整条消息。
- 首期不要求群聊 Agent 下载原始附件。

## 4. 核心概念

### 4.1 群聊与会话

群聊的参与成员全部是 Agent。人类用户通过输入框向群聊发起消息、上传附件、选择 Skill 和指定 Agent。

本需求中的“当前会话”与群聊生命周期一致：群聊被删除时，当前会话结束；关闭页面、刷新页面或一段时间没有消息，不视为会话结束。

### 4.2 主 Agent

主 Agent 是系统默认协调者，不出现在 `@Agent` 列表中。主 Agent 负责：

- 接收未指定 `@Agent` 的消息。
- 理解消息、附件和 Skill 语义。
- 在未指定 Agent 时进行自动分发。
- 协调多个 Agent 的协同执行。
- 汇总最终结果、临时结果和重新汇总结果。

### 4.3 Skill

Skill 是可以被 Agent 使用的能力。Skill 通过插件注册中心进行登记、分类、启用、停用和版本管理。

首期 Skill 不需要预先绑定某个 Agent。没有 `@Agent` 时由主 Agent 根据语义选择执行者；有 `@Agent` 时，在用户指定的 Agent 范围内进行语义路由。

### 4.4 Agent

Agent 来自独立的 Agent 管理模块，不属于插件注册中心的注册对象。Agent 管理模块负责 Agent 的基础配置、权限、启用状态、分类和可用性。

### 4.5 结构化 Tag

输入框和聊天记录中展示以下结构化 Tag：

- `/Skill`：表示要执行的能力。
- `@Agent`：表示负责完成需求的 Agent 候选。
- 图片缩略图：表示图片附件引用。
- 文件预览 Tag：表示文件附件引用。

Tag 既有可读展示文本，也有结构化 ID、类型、版本和关联关系。

## 5. 用户输入与 Tag 规则

### 5.1 `/Skill` 规则

- 一条消息最多只能选择一个 `/Skill`。
- 输入 `/` 后打开 Skill 分类列表。
- `/` 下拉不支持关键词搜索，只通过分类和列表选择。
- 分类为一级分类，不支持首期多级嵌套。
- 每个 Skill 必须且只能归属一个分类。
- 分类和 Skill 均按名称排序。
- 未选择 Skill 时，`/` 可以作为普通字符发送。
- Skill Tag 支持单独删除和重新选择替换。

### 5.2 `@Agent` 规则

- 一条消息可以选择多个 `@Agent`。
- 输入 `@` 后必须选择 Agent；未选择时不能将 `@` 作为普通字符发送。
- Agent 列表展示当前用户有权限使用的全部 Agent。
- 主 Agent 不出现在列表中。
- Agent 列表支持分类/分组和按名称、显示名称、描述进行实时搜索。
- `@Agent` Tag 支持单独删除和重新选择替换。
- 选择尚未加入当前群聊的 Agent 时，先提示用户确认；用户确认后，该 Agent 加入当前群聊。
- 新加入的 Agent 可以读取加入前的聊天记录和附件。
- Agent 加入后持续参与当前群聊；群聊被删除时退出。
- 本期不设计 Agent 主动移除能力。

### 5.3 `/` 与 `@` 的组合规则

- `/Skill` 与 `@Agent` 可以任意顺序选择。
- `/Skill` 表示能力；`@Agent` 表示负责完成需求并使用该能力的 Agent。
- 有一个 `/Skill` 和多个 `@Agent` 时，系统根据语义在这些 Agent 中选择一个最匹配的 Agent 执行 Skill。
- 如果指定的 Agent 都不适合，任务回退给主 Agent。
- 没有 `@Agent` 时，主 Agent 负责处理 Skill，并可以根据语义将需求分发给多个 Agent。
- 没有 `/Skill` 时，消息仍可作为普通自然语言需求处理。

### 5.4 Tag 展示与保存

- `/Skill` 和 `@Agent` 使用固定的系统颜色、字体和图标规范进行区分。
- 图片显示缩略图；文件显示文件预览 Tag。
- 发送前所有 Tag 和附件都可以单独删除。
- 发送后聊天记录继续显示 Tag。
- 发送消息时同时保存可读文本和结构化引用数据。
- Agent 执行时以结构化引用数据为准，不依赖从普通文本反向解析 Tag。

## 6. 附件需求

### 6.1 上传范围与限制

一条消息最多支持：

- 4 张图片。
- 4 个文件。
- 图片和文件可以混合上传，总附件数最多 8 个。

单个附件大小上限：

- 图片：10 MB。
- 文件：50 MB。

首期支持的格式：

- 图片：JPG/JPEG、PNG、GIF、WEBP。
- 文件：PDF、DOC、DOCX、XLS、XLSX、PPT、PPTX、TXT。

不支持 ZIP、RAR 等压缩包。

### 6.2 上传者与访问权限

- 只有人类用户可以上传附件。
- Agent 不能主动上传附件。
- 所有群聊 Agent 都可以查看和引用群聊附件。
- 本期不要求群聊 Agent 下载附件。

### 6.3 图片处理

图片上传后立即进入内容理解流程。

图片状态至少包括：

1. `uploading`：上传中。
2. `recognizing`：内容识别中。
3. `ready`：识别完成。
4. `recognition_failed`：识别失败。

首期图片识别要求：

- 支持图片内容理解和自然语言描述。
- 暂不支持 OCR 文字识别。
- 识别完成后在附件区域显示识别摘要。
- 用户可以查看识别摘要，但不能编辑识别结果。
- 识别结果作为 Agent 上下文的一部分保存。
- 识别失败时保留原图，显示失败状态并支持重试。
- 只要原图上传成功，即使识别失败，也不阻止用户发送消息。

### 6.4 文件处理

- 文件上传后只保存原始二进制和文件元数据。
- 上传阶段不自动提取全文、不自动生成摘要。
- 文件作为当前消息上下文自动挂载，但不把全文无条件注入模型上下文。
- Agent 需要使用文件时，通过文件 ID 和元数据调用文件读取能力按需读取。

### 6.5 上传失败

- 单个附件上传失败时，显示失败状态。
- 用户可以单独重试失败附件。
- 用户可以单独删除失败附件。
- 其他已成功上传的附件不受影响，可以继续发送。

### 6.6 附件生命周期

- 附件在群聊存在期间持续保留。
- 群聊删除时，群聊附件一并删除。
- 发送后不能单独删除附件。
- 删除包含附件的整条消息时，同步删除该消息关联的附件。
- 被删除的附件不能被后续消息继续引用。

### 6.7 附件路由

- 没有指定 `@Agent` 时，主 Agent 首先接收附件上下文，再根据消息语义和附件内容分发任务。
- 指定了 `@Agent` 时，在指定 Agent 范围内进行语义路由。
- 如果指定 Agent 不适合处理附件或 Skill，回退给主 Agent。

## 7. Skill 插件注册中心

### 7.1 分层范围

Skill 支持三个管理层级：

1. 系统级：全局可用。
2. 群聊级：当前群聊可用。
3. 个人级：默认只有创建者本人可用。

同名 Skill 的优先级为：

```text
个人级 > 群聊级 > 系统级
```

高优先级 Skill 可以覆盖低优先级同名 Skill。

### 7.2 管理权限

- 系统级 Skill：系统管理员维护。
- 群聊级 Skill：群聊管理员维护。
- 个人级 Skill：用户自己维护。
- 个人级 Skill 可以直接升级为群聊级 Skill，不需要审批。
- 升级为群聊级后，按群聊级规则由群聊管理员维护。

### 7.3 Skill 基础字段

每个 Skill 至少应具备：

- 唯一标识。
- 名称。
- 显示名称。
- 描述。
- 所属分类。
- 管理层级。
- 创建者/维护者。
- 当前版本。
- 启用状态。
- 可执行入口或能力定义。
- 创建时间、更新时间。

### 7.4 状态与版本

- Skill 支持启用和停用。
- 停用 Skill 不出现在 `/` 下拉列表中。
- 历史消息中的 Skill Tag 保留原名称和结构化引用。
- 历史消息重新执行时使用当前最新的启用版本。

### 7.5 分类管理

- 分类为一级分类。
- 分类可以动态创建、重命名和管理。
- 每个 Skill 只能归属一个分类。
- 删除分类前必须先将其中全部 Skill 迁移到其他分类。
- 不允许删除仍包含 Skill 的分类。
- `/` 列表中的分类和 Skill 按名称排序。

## 8. Agent 管理与加入群聊

### 8.1 Agent 数据来源

- Agent 由独立的 Agent 管理模块提供。
- Agent 不是插件注册中心对象。
- Agent 管理模块负责基础配置、分类、启用状态、权限和可用性。

### 8.2 Agent 可用性

`@Agent` 列表只展示当前用户：

- 有权限使用的 Agent。
- 已启用的 Agent。
- 当前可用的 Agent。

已停用或已删除 Agent 不进入新消息的 `@` 列表。

### 8.3 外部 Agent 加入流程

当用户选择一个尚未加入当前群聊的 Agent：

1. 系统显示加入确认。
2. 用户确认后，Agent 加入当前群聊。
3. Agent 可以读取该群聊已有消息和附件。
4. Agent 持续参与该群聊，直到群聊被删除。

管理员不负责替用户确认加入，但负责 Agent 的基础配置和可用状态。

## 9. 路由、协同与执行

### 9.1 有 `@Agent` 的消息

- `@Agent` 列表代表用户允许参与本条消息处理的 Agent 候选范围。
- 当候选有多个时，主 Agent 根据需求、附件和 Skill 语义选择一个最匹配的 Agent。
- `/Skill` 最终只由一个 Agent 使用和执行。
- 如果候选 Agent 均不匹配，回退给主 Agent。

### 9.2 无 `@Agent` 的消息

- 主 Agent 接收完整消息上下文。
- 主 Agent 可以根据语义将任务分发给多个 Agent 协同处理。
- 分发数量和具体 Agent 由主 Agent 根据任务决定。
- 最终结果始终由主 Agent 汇总并统一回复。

### 9.3 协同任务面板

协同过程使用统一任务面板展示：

- 被分发的 Agent 列表。
- 每个 Agent 的状态和进度。
- 每个 Agent 的阶段性输出。
- Skill 执行状态。
- 附件读取和处理状态。
- 成功、失败、取消和重试信息。

任务面板在任务完成后仍保留在聊天记录中，用户可以按 Agent 展开查看完整过程。

### 9.4 失败、取消和重试

- 一个 Agent 失败时，其他 Agent 继续执行。
- 主 Agent 汇总已成功结果，并标记失败 Agent。
- 用户可以中止整个协同任务。
- 用户可以单独重试失败 Agent。
- 中止后保留已完成结果，并由主 Agent 生成当前阶段临时汇总。
- 单独重试完成后，不自动更新主 Agent 汇总。
- 用户主动点击“重新汇总”后，才生成新的汇总结果。
- 重新汇总默认纳入所有已完成和重试成功的 Agent 结果。
- 新汇总以新版本追加保存，原汇总继续保留。
- 所有汇总均由主 Agent 处理。

## 10. 消息、上下文与持久化

### 10.1 消息结构

每条用户消息至少需要保存：

- 原始可读文本。
- 结构化 Skill 引用，可为空。
- 结构化 Agent 引用列表，可为空。
- 附件引用列表，可为空。
- 消息所属群聊和发送者。
- 消息创建时间。
- 当前路由结果。
- 关联的协同任务和汇总版本。

### 10.2 附件结构

每个附件至少需要保存：

- 附件 ID。
- 所属群聊和消息 ID。
- 原始文件名。
- MIME 类型。
- 文件大小。
- 存储位置或对象引用。
- 上传状态。
- 图片识别状态（图片适用）。
- 图片识别摘要（图片适用）。
- 创建时间和删除时间。

### 10.3 历史消息

- 历史消息保留可读文本和结构化引用。
- 历史 Skill Tag 保留名称；重新执行使用当前最新启用版本。
- Agent 被停用或删除后，历史 `@Agent` Tag 保留，但不能再次执行。
- 删除消息会同步删除消息附件和对应附件引用。

## 11. 关键状态与异常处理

### 11.1 Skill 状态

```text
disabled -> enabled
enabled -> disabled
```

停用只影响新消息选择，不删除历史 Tag。

### 11.2 Agent 状态

Agent 至少需要区分：

- 可用且有权限。
- 无权限。
- 已停用。
- 已删除。
- 当前不可用。

只有“可用且有权限”的 Agent 出现在 `@` 列表。

### 11.3 失败回退

- 指定 Agent 不支持 Skill：回退主 Agent。
- 多个指定 Agent 均不适配：回退主 Agent。
- 图片识别失败：保留原图，允许重试，仍可发送。
- 文件上传失败：只影响失败附件，其他附件可继续发送。
- 单个协同 Agent 失败：其他 Agent 继续，主 Agent 标记失败项并汇总成功结果。

### 12.4 权限与生命周期

- [ ] 个人 Skill 可以无审批升级为群聊级 Skill。
- [ ] 停用 Skill 不出现在新消息列表，历史 Tag 保留。
- [ ] 主 Agent 不出现在 `@` 列表。
- [ ] 选择群外 Agent 时需要用户确认。
- [ ] 群聊删除时，附件和当前加入的 Agent 关联一并结束。

## 13. 实现约束与风险

### 13.1 实现约束

- Agent、Skill、附件和协同任务需要使用稳定 ID 进行结构化关联。
- 原始文本展示与结构化执行数据必须分离，避免依赖文本解析执行。
- 文件内容应按需读取，避免上传时将完整内容无条件注入模型上下文。
- 路由结果、Agent 状态、附件状态和汇总版本应进入统一事件/持久化链路。
- 历史消息必须保留足够的展示信息，即使 Skill 或 Agent 后续停用、删除。

### 13.2 主要风险

- 图片识别摘要属于模型生成内容，需要避免将不确定描述当作事实写入业务决策。
- 文件按需读取需要严格校验群聊、消息和附件权限，避免跨群聊访问。
- 个人级覆盖系统级和群聊级时，可能产生同名 Skill 的理解偏差，需要在 UI 中明确来源层级。
- 多 Agent 中间结果持久化量较大，需要控制事件体积和历史加载策略。
- 删除消息同步删除附件时，需要处理已经被其他消息引用的关联关系。

## 14. 后续可扩展方向

- 插件注册中心扩展 Tool、Command 等类型。
- 图片 OCR、多语言识别和表格/文档视觉解析。
- Skill 版本锁定和历史版本重放。
- 更细粒度的 Skill 权限、审批和发布流程。
- Agent 主动邀请、移除和群聊成员编排。
- 附件引用关系图和跨消息附件检索。
- 协同任务模板、可配置路由策略和 Agent 能力矩阵。

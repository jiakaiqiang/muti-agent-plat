# 工作流编排与 Agent 能力画像路线 v1

## 1. 当前版本范围

当前版本以可审计的线性 Agent 工作流为主，不实现通用低代码执行引擎。

已落地能力：

- `WorkflowDefinition`、Agent 节点、线性连线、版本和状态合同。
- 多工作流 CRUD 与 file/PostgreSQL JSONB collection 持久化。
- 左侧 Agent 资源、右侧画布；支持添加、拖入、重排、删除和显式保存。
- 用户确认任务契约后进入 `WAIT_WORKFLOW_SELECT`，选择保存后的工作流再执行。
- 工作流节点按依赖严格串行；节点输出写入群聊并进入 `WAIT_WORKFLOW_STEP_CONFIRM`。
- 用户选择“确认并继续”后推进下一节点；选择“要求修改”时，修改要求写入群聊并重跑当前节点。

当前非目标：

- 条件、并行、汇聚、循环和子工作流节点。
- Tool、MCP、定时器和外部事件节点。
- 工作流发布审批、版本回滚和模板市场。
- 根据能力画像自动替换工作流中的固定 Agent。

人工确认和机器人确认节点已经纳入下一阶段的确认范围，但不应描述为当前已落地能力。

## 2. 已确认下一阶段：低代码工作流创建页

工作流创建页采用参考图所示的浅色、三栏低代码编排方式。页面服务于工作流定义和发布，不复用群聊中的运行态工作流视图。

### 2.1 页面结构

- 顶部基础信息区：编辑工作流名称和描述，并展示长度限制、保存草稿、发布和返回操作。
- 左侧资源面板：按 `Agent`、`人工确认`、`机器人确认` 三个分组展示可拖入画布的节点资源。
- 中间流程画布：展示开始、业务节点、确认节点、连接线和结束节点，并提供撤销、重做、删除、对齐、缩放和画布定位工具。
- 右侧属性面板：展示当前选中节点的详情、配置和输入输出；没有选中节点时展示工作流摘要和发布前校验结果。

三栏应保持稳定布局：左侧用于查找和添加资源，中间承担主要编排操作，右侧只编辑选中对象，不能在多个区域重复放置同一组配置项。

### 2.2 左侧资源分组

`Agent` 分组：

- 支持按名称搜索，并按需求分析、开发工程、测试运维、产品设计等现有 Agent 分类筛选。
- 每个资源项显示图标、名称、能力摘要和分类标签。
- 支持点击添加和拖拽添加；同一个 Agent 可以在一个工作流中出现多次，每次形成独立节点。

`人工确认` 分组：

- 提供人工确认节点模板，默认确认人为当前会话发起人。
- 节点支持“通过并继续”“退回上一 Agent 修改”“终止工作流”三种决策。
- V1 不提供候选用户、用户组、委托和超时升级配置。

`机器人确认` 分组：

- 提供机器人确认节点模板，创建后必须选择一个评审 Agent。
- 节点配置评审说明、通过标准、最大返工次数；默认最大返工次数为 `2`。
- 评审结果固定为 `approve/revise/reject`；执行异常、结果格式错误或重试超限时转为人工确认。

资源分组可折叠，但分组标题和节点数量始终可见。搜索仅过滤 Agent，不隐藏人工确认和机器人确认入口。

### 2.3 中间流程画布

- 画布使用浅色点阵背景，开始和结束节点固定存在且不可删除。
- 节点之间的连接线上提供 `+` 插入入口，可以直接选择 Agent、人工确认或机器人确认。
- 支持从左侧拖拽到连接线或节点之间，也支持点击资源后插入当前选中节点之后。
- 选中节点使用明确描边，连接线和节点状态色只表达类型与校验状态，不表达尚未发生的运行状态。
- V1 只允许单开始、单结束的线性流程；参考图中的分支布局仅作为后续 DAG 画布预留，不进入本期执行语义。
- 保存或发布前校验空流程、断链、环路、失效 Agent、机器人确认缺少评审 Agent，以及确认节点没有上游 Agent。

### 2.4 右侧节点属性

- Agent 节点：展示 Agent 基本信息、能力、标签；可配置节点名称、阶段说明、输入约定和输出约定。
- 人工确认节点：配置确认标题、确认说明、展示给用户的输出摘要和允许操作；确认人固定显示为会话发起人。
- 机器人确认节点：配置评审 Agent、评审提示、通过标准、最大返工次数和失败转人工说明。
- 开始/结束节点：只展示只读说明和全局输入输出摘要，不提供删除操作。
- 修改属性后应立即反映在画布节点摘要中，但只有保存草稿或发布成功后才写入服务端定义。

### 2.5 创建页验收

- 三类资源分组清晰可辨，搜索 Agent 时确认节点入口仍可见。
- 三类节点均能通过拖拽或点击加入线性流程，并能从连接线 `+` 入口插入。
- 选择任意节点后，右侧只显示与该节点类型对应的属性。
- 撤销、重做、删除、缩放和定位不会改变未涉及节点的数据。
- 不合法流程不能发布，并能在画布节点和右侧校验区定位原因。
- 草稿可以继续编辑；发布版本不可变，后续修改必须形成新版本。

## 3. 后续阶段：Agent 能力画像匹配

低代码创建页和确认节点完成后，在不破坏固定 Agent 工作流的前提下，引入可解释的能力画像匹配。

### 3.1 能力画像输入

```ts
type AgentCapabilityProfile = {
  agentId: string
  roleKeys: string[]
  capabilityIds: string[]
  skillKeys: string[]
  toolKeys: string[]
  knowledgeScopes: string[]
  tags: string[]
  runtimeEligibility: string[]
  historicalSignals?: {
    completed: number
    blocked: number
    rejected: number
    validationPassed: number
  }
}
```

画像只能来自可追溯的 Agent Profile、Capability、Skill、Tool Catalog、Knowledge grant、Runtime eligibility 和历史执行事件，不允许从展示名称直接推断能力。

### 3.2 工作流能力槽位

工作流节点扩展为两种绑定模式：

- `fixed_agent`：继续使用当前 `agentId` 固定绑定。
- `capability_slot`：声明角色、能力、Skill、Tool、知识和 Runtime 约束，由匹配器从用户允许的 Agent 集合中选择候选。

匹配结果必须保存：候选列表、硬约束淘汰原因、评分维度、最终选择原因和用户覆盖记录。

### 3.3 匹配规则

1. 先检查状态、权限、Tool Authority、Workspace 能力和 Runtime eligibility 等硬约束。
2. 再按角色、Capability、Skill、知识覆盖和历史验证信号评分。
3. 低置信度、并列候选或高风险节点必须请求用户选择。
4. 匹配范围默认限制为用户选择的 Agent；工作流显式允许扩展候选时仍需用户确认。
5. Agent 拒绝或阻塞后只产生改派建议，Coordinator 仍是唯一 assignee 写入方。

### 3.4 能力画像阶段验收

- 每个能力槽位都能展示“为什么选中该 Agent”。
- 缺少硬约束时 fail closed，不退化为第一个 Agent。
- 固定 Agent 工作流行为保持不变。
- 匹配决策、用户覆盖和改派均进入事件流。
- 至少覆盖能力完全匹配、无候选、并列候选、Runtime 不可用和执行中拒绝五类测试。

## 4. 后续工作流增强

能力画像阶段完成后，再依次考虑条件/并行/汇聚、节点级 Runtime/模型、版本回滚与差异比较、Scenario 模板、Autopilot 绑定和运行轨迹回放。

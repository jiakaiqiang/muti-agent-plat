# 多 Agent 上下文接续修复（方案 B）

日期：2026-10-11。

## 问题与范围

原会话 `466efa14-9a59-433a-8f42-e1c6521100eb` 在需求分析师成功补读 8 个文件并完成 Codex 调用后，系统架构师仍在模型调用前触发 `evidence-empty`。索引入口和版本已正常，本次故障是讨论参与者提前装配上下文，与会话级补读去重之间的衔接遗漏。

用户确认方案 B：沿用 Context v2，修复调用前装配、有效缓存复用、补读去重、并发一致性，并验证真实多 Agent 流程。证据门禁、工作区版本检查、敏感/二进制过滤和输入预算继续生效。

## 实现

- 首次讨论与追问讨论在参与者实际开始执行时创建上下文；公共 Runtime 入口仅刷新当前角色/工作项已选择的证据引用，保留专属指令。
- 每个逻辑 Runtime 调用独立记录补充请求。会话历史用于审计和缓存导航，不再代表当前调用已经拿到正文。
- 同一会话的补读批次排队执行并合并缓存；模型执行仍可并发。后续同文件请求复用当前版本有效缓存。批次保留自己的证据副本，避免后续读取另一片段覆盖当前调用的正文。
- 文件请求按路径、行段、字节上限判重；不同片段可同时进入 L3。完整读取不能复用局部/截断缓存，完整读取会清除旧行段元数据。
- `hydratedFiles` 只记录本批实际保留的请求，读取上限导致的延后片段不参与成功去重。
- 补读历史记录可选 `workItemId`，路由和额外证据路径授权按工作项筛选。历史无工作项记录不会自动提升到新工作项；有明确任务匹配的旧记录保留兼容。
- 补读记录提供 `cachedPaths` / `readPaths`；调用前记录 `CONTEXT_EVIDENCE_ASSEMBLED` 的实际 L3 路径、字节、截断和门禁状态；无新增请求或预算耗尽记录 `CONTEXT_SUPPLEMENT_STOPPED`。
- 排队中止的补读不会继续读取或提交缓存，失败后释放队列。

变更集中于编排模块、补读去重、Context v2 编译及共享合同的可选元数据字段。无数据库迁移。
